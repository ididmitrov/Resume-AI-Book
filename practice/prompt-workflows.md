# Exercise: Prompt Workflows — решения

Попълнено упражнение към **Prompt Engineering**, SoftUni AI. За всяка стъпка: готов prompt, примерен изход и едно изречение защо е така.

**Трите техники:** Chaining = отделни prompt-ове, изходът на N влиза в N+1. Decomposition = MECE подзадачи, после синтез. Multi-step = един разговор с няколко хода.

---

# 1. Prompt Chaining — анализ на отзиви

Всяка стъпка прави едно нещо. Ако смесите категоризация + Топ 3 + план в един prompt, изходът става каша.

**Отзиви:** 1. „Интерфейсът е объркващ, не намирам бутона за запис.“ 2. „Зарежда бавно на мобилен.“ 3. „Страхотно! Точно това търсех.“ 4. „Цената е висока за това, което предлагате.“ 5. „Нотификациите идват в грешно време.“ 6. „Синхронизацията с Google Calendar не работи.“ 7. „Поддръжката отговори бързо и помогна.“ 8. „Липсва dark mode.“ 9. „Изтри ми данните след ъпдейт!“ 10. „Перфектно за екипна работа.“

---

## Стъпка 1 — Категоризация

Само таксономия. Без решения и без Топ 3 — иначе следващата стъпка няма чист вход.

**Prompt**

```text
Роля: Ти си старши UX researcher в SaaS продукт.

Задача: Категоризирай следните 10 клиентски отзива. Не предлагай решения. Не приоритизирай. Не пиши резюме за мениджмънт.

Отзиви:
1. "Интерфейсът е объркващ, не намирам бутона за запис."
2. "Зарежда бавно на мобилен."
3. "Страхотно! Точно това търсех."
4. "Цената е висока за това, което предлагате."
5. "Нотификациите идват в грешно време."
6. "Синхронизацията с Google Calendar не работи."
7. "Поддръжката отговори бързо и помогна."
8. "Липсва dark mode."
9. "Изтри ми данните след ъпдейт!"
10. "Перфектно за екипна работа."

Правила:
- Всеки отзив в точно една основна категория. Вторичен нюанс — в колона „Вторична тема“.
- Стабилни имена на категории, не по един етикет на отзив.
- Сантимент: negative / mixed / positive.
- Тежест: P0 критичен инцидент; P1 блокиращ; P2 търкане; P3 пожелание; P4 похвала.
- Не измисляй факти, които ги няма в отзива.

Формат: таблица с колони №, Цитат, Основна категория, Вторична тема, Сантимент, Тежест, 1-изреченска обосновка.
После: списък „Категории и брой“.
```

**Изход**

| № | Цитат | Основна категория | Тежест |
| :-: | :--- | :--- | :---: |
| 1 | Интерфейсът е объркващ, не намирам бутона за запис. | UX / discoverability | P1 |
| 2 | Зарежда бавно на мобилен. | Performance (mobile) | P1 |
| 3 | Страхотно! Точно това търсех. | Product-market fit / похвала | P4 |
| 4 | Цената е висока за това, което предлагате. | Pricing / perceived value | P2 |
| 5 | Нотификациите идват в грешно време. | Notifications | P2 |
| 6 | Синхронизацията с Google Calendar не работи. | Integrations / reliability | P1 |
| 7 | Поддръжката отговори бързо и помогна. | Customer support | P4 |
| 8 | Липсва dark mode. | Feature request / accessibility | P3 |
| 9 | Изтри ми данните след ъпдейт! | Data integrity / release quality | P0 |
| 10 | Перфектно за екипна работа. | Collaboration value / похвала | P4 |

| № | Вторична тема | Сантимент | Обосновка |
| :-: | :--- | :--- | :--- |
| 1 | Onboarding | negative | Save не се намира — блокира ежедневна употреба. |
| 2 | — | negative | Мобилната скорост е хигиена. |
| 3 | — | positive | Силен сигнал за ценност. |
| 4 | — | negative | Възприемана стойност, не технически дефект. |
| 5 | UX | negative | Функцията работи, таймингът дразни. |
| 6 | Calendar | negative | Обещана интеграция е счупена. |
| 7 | — | positive | Оперативен актив. |
| 8 | UI polish | mixed | Пожелание, не блокер. |
| 9 | Trust | negative | Загуба на данни = критичен инцидент. |
| 10 | — | positive | Потвърждава core value. |

Категории: по 1 отзив във всяка тема. Тежестта не е равномерна — P0 е само №9.

*Защо:* тежестта P0–P4 и забраната за решения пазят веригата — ако data loss влезе като „bug“ редом с dark mode, целият chain после е грешен.

## Стъпка 2 — Топ проблеми

Вход = изходът от Стъпка 1, не суровите 10 цитата.

**Prompt**

```text
Роля: Ти си Head of Product. Получаваш вече категоризирани отзиви — не ги прекатегоризирай от нулата.

Задача: Изведи Топ 3 проблема за следващия спринт/release, плюс 2 неща, които НЕ трябва да пипаме сега.

Вход (изход от Стъпка 1 — категоризация):
[ПОСТАВЕТЕ ТУК ЦЕЛИЯ ИЗХОД ОТ СТЪПКА 1]

Критерии (в този ред):
1. Риск за доверие / churn / правни последици
2. Счупена обещана функционалност
3. Хигиена, която блокира ежедневна употреба (P1)
4. Възприемана стойност — само ако има продуктов лост, не „намалете цената“
5. Пожелания (P3) остават извън Топ 3

Ограничения:
- Топ 3 са проблеми, не похвали.
- За всеки: доказателство, защо сега, риск при бездействие, какво НЕ знаем още.
- Положителните сигнали — отделно, те са актив.
- Не пиши action plan.

Формат:
A. Топ 3 (Ранг, Проблем, Категория, Тежест, Доказателство, Защо сега, Риск, Неизвестни)
B. Извън скоупа този цикъл (2–3 item-а + защо)
C. Положителни активи
```

**Изход**

| Ранг | Проблем | Категория | Тежест | Доказателство |
| :-: | :--- | :--- | :---: | :--- |
| 1 | Загуба на данни след ъпдейт | Data integrity | P0 | №9 |
| 2 | Счупена Google Calendar sync | Integrations | P1 | №6 |
| 3 | Бутонът Save не се намира | UX / discoverability | P1 | №1 |

| Ранг | Защо сега | Риск при бездействие | Неизвестни |
| :-: | :--- | :--- | :--- |
| 1 | Унищожава доверие с едно събитие | Отлив, репутация, възможен compliance | Колко акаунта; backup; кой release |
| 2 | Обещана интеграция, която не работи | Тихи откази; повече CS тикети | OAuth vs sync job; откога |
| 3 | Основно действие е скрито | „Продуктът е сложен“; по-слабо възприемане на цената (№4) | Нов vs стар потребител; кой екран |

Извън скоупа: dark mode (P3), тайминг на нотификации (P2), сваляне на цена (първо reliability). Следващ кандидат: мобилна скорост (№2).

Активи за запазване: product-market fit (№3), силна поддръжка (№7), екипна работа (№10).

*Защо:* без явни критерии Топ 3 става „най-шумното“. Колоната „Неизвестни“ спира следващата стъпка да халюцинира фикс без одит.

## Стъпка 3 — Action plan

Само Топ 3. Капацитетът е в prompt-а, иначе моделът пише програма за 40 души.

**Prompt**

```text
Роля: Ти си Staff engineer + Product Operations lead в малък SaaS екип.

Задача: 30-дневен action plan САМО за Топ 3 проблема. Не добавяй нови инициативи, освен минимални discovery стъпки.

Вход (изход от Стъпка 2):
[ПОСТАВЕТЕ ТУК ЦЕЛИЯ ИЗХОД ОТ СТЪПКА 2]

Капацитет:
- 1 backend, 1 frontend, 1 QA, CS от 2 души
- Един production hotfix прозорец седмично
- Не обещавай нови големи фийчъри

За всеки от Топ 3: Immediate (0–72ч), Short-term (дни 3–14), Verify (дни 14–30), Owner (роля), съобщение към засегнатите (1 абзац, честен тон).

Формат: план по проблем; 30-дневен timeline по седмици; Definition of Done; non-goals.
Не пиши Executive Summary.
```

**Изход (съкратен)**

Non-goals: dark mode, ценообразуване, нотификации, нови collaboration фийчъри.

| Проблем | Immediate | Short-term | Verify / Done |
| :--- | :--- | :--- | :--- |
| P0 данни след ъпдейт | Rollback / kill switch, одит на засегнатите, restore playbook, status page | Root cause на миграцията, фикс + upgrade тестове, postmortem в pipeline | 0 нови случаи 14 дни; restore със статус до 24ч |
| P1 Calendar sync | Метрики на грешките, reconnect UX вместо тих fail, CS макро | Фикс на token/sync, retry, canary акаунт | ≥99% sync за 7 дни |
| P1 Save CTA | Replay / 5 теста къде търсят Save | Sticky/primary Save, без redesign | Видим без scroll; спад в „къде е запис“ тикети |

Седм. 1: P0 containment + Calendar диагностика + Save discovery. Седм. 2: фиксове. Седм. 3: guardrails + canary. Седм. 4: verify.

Съобщения: честно за data loss („спряхме ъпдейта, възстановяваме“); reconnect за календара; „правим Save видим“ без да сменяме workflow-а.

*Защо:* P0 иска containment преди фикс. Non-goals пазят от „щом сме в UI-а, да сложим и dark mode“.

## Стъпка 4 — Executive Summary

Синтез от стъпки 2 и 3. Не суровите отзиви — иначе chaining-ът се е разпаднал.

**Prompt**

```text
Роля: Ти си VP Product. Пишеш към CEO и Head of CS.

Задача: Едностраничен Executive Summary само от двата входа. Не преоткривай Топ 3. Не добавяй нови проблеми.

Вход A — Топ проблеми (Стъпка 2):
[ПОСТАВЕТЕ ИЗХОДА ОТ СТЪПКА 2]

Вход B — Action plan (Стъпка 3):
[ПОСТАВЕТЕ ИЗХОДА ОТ СТЪПКА 3]

Изисквания: ~400 думи; спокоен тон; без паника и без прикриване на P0; без жаргон; не измисляй числа.
Формат: заглавие; ситуация; приоритети; план за 30 дни (Приоритет, Действие, До кога, Сигнал); решение от мениджмънта; рискове и non-goals; какво работи.
```

**Изход**

**Customer Feedback Chain — 30-дневен фокус**

От 10 отзива три са похвали (продукт, екипна работа, поддръжка). Отрицателните теми са различни, но тежестта не е: P0 е загуба на данни след ъпдейт. До него — счупен Calendar и ненамерим Save. Цената изглежда висока, но няма смисъл да я режем преди reliability. Dark mode и нотификации остават извън цикъла.

| Приоритет | Действие | До кога | Сигнал |
| :--- | :--- | :--- | :--- |
| P0 данни | Rollback, одит, restore, фикс на upgrade path | Седм. 1–3 | 0 нови случаи 14 дни |
| P1 Calendar | Грешки + reconnect + фикс + canary | Седм. 1–4 | ≥99% sync / 7 дни |
| P1 Save | Тестове + видим CTA | Седм. 1–3 | Save без scroll |

Ask: 30-дневен freeze на нови фийчъри; CS ескалира data-loss като P0; един hotfix прозорец седмично. Не знаем още колко акаунта са засегнати — първата седмица е одит.

*Защо:* лимитът на думи спира преразказа на плана. Забраната за нови проблеми спира финалния синтез да „открие“ SSO и Q4 vision.

## Рефлексия за Раздел 1

**Имаше ли пренесена грешка?** Да — ако Стъпка 1 сложи data loss като P2, Топ 3 и планът оптимизират polish вместо инцидент. Затова има P0–P4 и забрана да се измислят факти. Ако Стъпка 2 дропне похвалите, Summary-то звучи като криза въпреки №3, №7, №10.

**Какво бихте променили?** При повече отзиви — колона „сегмент“. В Стъпка 2 — „не групирай несвързани P2-та, за да напълниш Топ 3“. В Стъпка 3 — реални story points. В Стъпка 4 — фиксиран език (BG или EN).

# 2. Task Decomposition — лонч план

Сценарий: лонч на **HR онбординг автоматизация**. Подзадачите са успоредни (MECE), не верига.

MECE = без припокриване + заедно покриват цялата цел.

---

## Стъпка 1 — MECE декомпозиция

**Главна цел:** успешен лонч за 6 седмици — ползва се, екипите могат да я носят, phased rollout, ясни go/no-go метрики.

| Подзадача | Покрива | Нарочно не покрива |
| :--- | :--- | :--- |
| 1. Скоуп и UX | v1 (документи, чеклист, напомняния, роли), v2, happy path + 3 failure state-а | Техническия „как“ на интеграциите |
| 2. Техническа готовност | HRIS/email/SSO, GDPR, QA, flags, rollback | Дефиницията „какво е продуктът“ |
| 3. GTM | Позициониране, in-app, email, changelog | Обучението на CS |
| 4. Enablement | Help center, макроси, battlecards, office hours | Външния анонс |
| 5. Rollout и метрики | Пилот → 10% → 50% → 100%, KPI, kill criteria | GTM текстовете |

**MECE?** Да: различен артефакт и owner. „Onboarding на потребителя“ е в 1, „onboarding на CS“ е в 4. Интеграциите: 1 казва *кои* са in-scope, 2 казва *как* се правят.

---

## Стъпка 2 — Три подзадачи (1, 3, 5)

Избрани, защото най-често се сливат в един лош prompt. Всеки има роля, контекст, формат, ограничения.

### А — Скоуп

**Prompt**

```text
Роля: Senior Product Manager в SaaS за HR автоматизация.
Контекст: v1 на HR Onboarding Automation след 6 седмици. Купувач: HR admin. Потребители: HR, manager, new hire. Допълваме HRIS, не го заменяме.
Задача: v1 scope brief.
Ограничения: макс 3 задължителни потока; без native mobile; GDPR — retention и роли, не правна експертиза.
Формат: problem statement; in-scope / out-of-scope; 3 user flows; 3 failure states; permissions; 6–8 Given/When/Then; макс 5 open questions.
```

**Изход**

Problem: първата седмица се губи между таблици и имейли. v1 = чеклист + документи + напомняния за 3 роли.

| In v1 | Out (v2+) |
| :--- | :--- |
| Шаблон (задачи, срокове, owner) | HRIS write-back |
| Upload/approve на документи | Нов e-sign доставчик |
| Email напомняния D-7 / D-1 / D0 / D+3 | Slack bot, native app |
| Статус борда; покана с magic link | ATS, payroll |
| Read-only HRIS полета (име, дата, мениджър) | Benefits enrollment |

Flows: HR клонира шаблон → new hire качва документи по magic link → manager вижда своите 4 задачи. Success: в ден 1 required = Done или Waived.

Failure: файл над лимит; изтекъл линк; HRIS offline → ръчни данни + банер. Manager не вижда ID/договор.

Open: файлови лимити, e-sign, BG/EN, брой шаблони, contractor vs full-time.

### Б — GTM

**Prompt**

```text
Роля: Product Marketing Manager, B2B HR SaaS.
Контекст: анонс към съществуващи клиенти. Обещание: по-малко изгубени задачи, не „заменяме Workday“.
Задача: 3-седмичен GTM пакет.
Ограничения: без native app, AI, „100% безпроблемен лонч“; без CS скриптове (друг екип); всеки текст трябва да може да се защити от support в ден 1.
Формат: позициониране; primary + 2 supporting + 3 забранени фрази; календар D-14 до D+7; in-app ~90 думи; email; 6 FAQ.
```

**Изход**

For HR екипи, които губят стъпки между мениджър и new hire. Unlike таблица + 15 имейла, we даваме статуси и напомняния без смяна на HRIS.

Primary: „Първата седмица — видима, не разпиляна.“ Забранено: AI, HRIS замяна, mobile, „безпроблемен лонч“.

Календар: D-14 вътрешен preview; D-7 email към admins; D0 = пилот, не blast; D+2 walkthrough; D+7 follow-up.

FAQ: влиза ли в плана; пише ли в Workday (не във v1); вижда ли manager ID (не); може ли да се изключи (flag).

### В — Rollout / KPI

**Prompt**

```text
Роля: Product Operations + аналитик.
Контекст: 6 седмици, feature flags, без 100% в ден 1.
Задача: rollout с KPI и kill criteria.
Ограничения: макс 5 KPI; kill criteria изпълними за 48ч; без vanity метрики.
Формат: фази; KPI таблица; kill/pause; feedback loop; go/no-go преди широко пускане.
```

**Изход**

Фази: 0 = 3 friendly; 1 = 10%; 2 = 50% при чисти 7 дни; 3 = 100% opt-in (не default on).

| KPI | Цел | Owner |
| :--- | :--- | :--- |
| Activation (шаблон + покана / 7 дни) | ≥40% | PM |
| Time-to-complete | ≤120ч | Product |
| P0/P1 incident rate | ≤2 / 100 workspace | Eng + CS |
| Blocked > 48ч | ≤15% | PM |
| CS контакти / 100 поканени | ≤8 | CS |

Kill: data leak към manager, bounce >10%, объркана start date в ≥3 акаунта. Pause фаза 2 при лош time-to-complete без инцидент.

*Защо три отделни prompt-а:* един „напиши лонч план“ дава смесен документ — метриките стават маркетингови, скоупът става рекламен.

## Стъпка 3 — Синтез

Не пренаписва подзадачите. Хваща противоречията.

**Prompt**

```text
Роля: Group Product Manager. 45-мин kickoff с Eng, Design, CS, PMM.
Задача: Един Launch Brief от трите артефакта. Не променяй скоуп, обещания, KPI. Напрежението — в decision log, не го замазвай.

Вход 1 — Scope: [ПОДЗАДАЧА А]
Вход 2 — GTM: [ПОДЗАДАЧА Б]
Вход 3 — Rollout: [ПОДЗАДАЧА В]

Формат: цел и non-goals; какво пускаме; как го казваме; фази; KPI и kill; работи по отбори (6 седмици); decision log; дневен ред за 45 мин.
Ограничение: GTM не обещава 100% на D0, ако rollout-ът казва пилот. Синхронизирай датите.
```

**Изход — Launch Brief (ядрото)**

Non-goals: mobile, AI, HRIS write-back, forced default. Съобщение: „първата седмица видима“. D0 = пилоти, не масов email.

| Седмица | Eng | Design | PMM | CS |
| :---: | :--- | :--- | :--- | :--- |
| 1 | Flags, tenant isolation, rollback drill | Happy path + failures | Changelog, забранени фрази | Таг `onb-v1` |
| 2 | Magic link, HRIS fallback | Document visibility | Admin email за фаза 1 | Офис hours за пилотите |
| 3–4 | Reminders, canary | Blocked microcopy | Walkthrough | Weekly топ Blocked |
| 5–6 | Freeze scope; фаза 3 visibility | Polish само по kill | Opt-in notes | Battlecard |

Decision log: PMM искаше D0 анонс към всички; rollout го забранява → D0 = пилоти. Отворени: файлове, e-sign, език, billing — до край на седм. 1.

*Защо:* синтезът е успял, ако хване противоречието D0, а не го осредни.

# 3. Multi-Step — длъжностна характеристика

Един чат, минимум 4 хода. Артефактът е един (JD), затова не chain-ваме. Посоката има право да се промени.

Позиция: **AI Workflow Specialist** (prompt workflows за CS и Product, не ML инженер).

---

### Ход 1 — широка чернова

```text
Роля: Talent Partner в SaaS за HR автоматизация (80 души, Sofia + remote EU).

Задача: Първа чернова на JD за „AI Workflow Specialist“.
Ролята превръща повтарящи се CS/Product задачи в надеждни prompt workflows (chaining, decomposition, multi-step), не тренира модели.

Искам широка, честна чернова: за кого е; първите 6 месеца; must vs nice; как мерим успех.
Формат: JD в секции. Допускания в края. Не измисляй заплата и stack — питай ме 3 уточняващи въпроса.
```

**Изход (същност):** IC роля, не research scientist. 6 месеца: одит на 8–10 процеса, 5 production workflows, обучение на CS. Must: писмено мислене + практически LLM. Nice: CS фон, лек скриптинг. Допускане: hybrid Sofia, без custom model training.

3 въпроса: seniority? код или само prompt+процес? репорт към Product / CS / AI ops?

*Защо:* ако в ход 1 поискате „финална JD“, няма какво да итерирате.

---

### Ход 2 — уточнение

```text
Отговори:
1. Mid-level IC. Не управлява хора.
2. Не е software engineer. Лек скриптинг е плюс. Доставка: шаблони, evaluation, enablement.
3. Reporting към Head of Product, 50% време в CS.

Промени: махни всичко като ML Engineer; добави седмичен ритуал с CS lead; must = портфолио от 3 реални workflow-а, не сертификат; hybrid София, 3 дни офис; без заплата още.
Покажи diff v0 → v1, после пълната v1.
```

**Изход:** Mid IC към Product, embedded в CS. Must: 3 примера (вход, изход, слабо място). Не е за хора, които искат да тренират модели. Метрики: % драфтове приети без редакция; 0 PII инцидента.

*Защо:* конкретни „махни / добави“ + diff, за да не пренапише цялото.

---

### Ход 3 — ново изискване

```text
Ново от Board: ролята трябва да издържи audit за данни.

Добави към v1, без да вдигаш seniority:
- правила за PII (какво не влиза в публичен ChatGPT)
- owner на prompt library (версия, deprecation)
- интервю от 3 стъпки, едната практическа: 10 отзива → 4-step chain
- абзац „как работим с AI“: моделите грешат, човек накрая за клиентски текстове

Затегни езика. v2 за вътрешен review с Head of CS, не за job board.
Маркирай 3 места, където CS ще възрази.
```

**Изход:** PII не в публични LLM; library с owner и archive след 30 дни без употреба. Интервю: разговор → практическа верига → Head of CS. Възражения: практическата е твърде продуктова; PII забавя пилоти; dual-report към Product.

*Защо:* ново изискване в същия тред. В chaining това би било нова верига от нулата.

---

### Ход 4 — финал

```text
Head of CS:
- практическата да е 10 CS тикета, не продуктови отзиви
- must: макроси в helpdesk (Intercom/Zendesk-like)
- заплата 4 200–5 200 EUR gross — само във вътрешна бележка
- публичната JD до ~650 думи, на български, за кариерната страница

Дай: A) публична JD  B) вътрешна бележка (заплата, как оценяваме практическата, red flags)
Не преправяй мисията. vFinal.
```

**Изход — публична JD (ядро):** Mid IC, репорт Product, 50% в CS, hybrid София. Проектира workflows, държи library, пази PII, седмичен ритуал с CS. Успех за 6 месеца: 5 живи workflow-а, по-бързи CS чернови, 0 data инцидента. Не търсим ML инженер. Процес: разговор → 10 тикета като верига → Head of CS.

Вътрешно: заплата 4200–5200 EUR gross. Оценяваме структура и PII контрол, не „креативен тон“. Red flags: custom LLM, лепене на лични данни, нула измерен ефект.

*Защо ход 4:* „не преправяй мисията“ пази вече взетите решения.

---

## Рефлексия за Раздел 3

**Посоката Ход 1 → 4:** от generic AI роля към mid IC в Product, после audit/PII, после CS тикети + helpdesk макроси. Краят е по-оперативен от старта — нормално за multi-step.

**Ако беше Chaining?** Всеки ход = нов чат с копирана JD. Тонът скача, малка промяна („10 тикета“) ражда нова JD и губи мисията. Chaining е за *различен* артефакт на всяка стъпка. Тук артефактът е един.

# 4. Казус — PM под натиск

Данни: NPS 34 (беше 41); feature requests: bulk export, API, mobile; 2 enterprise с churn риск; onboarding wizard +18% activation; backlog 47, капацитет 12 pts.

Комбинация: decomposition → chaining (анализ → roadmap) → multi-step (churn) → синтез към Board.

---

## 4.1 Декомпозиция

Цел: честен Q3 review — защо NPS пада, какво влиза при 12 pts, как държим 2-та акаунта, какво искаме от Board.

| № | Подзадача | Техника |
| :-: | :--- | :--- |
| 1 | Ситуационен анализ (факти vs хипотези) | Chaining 4.2 |
| 2 | Q3 приоритети при 12 pts | Chaining 4.3 (вход = 4.2) |
| 3 | Churn за 2 named акаунта | Multi-step 4.4 |
| 4 | Board memo | Синтез 4.5 |

**MECE?** Да. (3) е отделна, защото enterprise churn често е CS/security, не само „сложи API в спринта“. NPS е симптом в (1), не отделен проект „вдигни NPS“.

---

## 4.2 Ситуационен анализ (Chaining)

Само диагноза. Без roadmap — иначе решенията се раждат от желания.

**Prompt**

```text
Роля: Product Director. Пишеш за себе си като PM, не за Board.
Задача: Ситуационен анализ. Само диагноза и хипотези. Без roadmap, без обещания, без слайдове.

Данни:
- NPS 34, беше 41 (Δ −7)
- Топ requests: bulk export, API, мобилно приложение
- 2 enterprise с churn риск (причини неизвестни)
- Onboarding wizard: +18% activation
- Backlog 47, капацитет 12 pts/спринт
- Продукт: HR automation SaaS

Правила: раздели факти / хипотези / неизвестни. Не измисляй причина за NPS, освен като хипотеза + как се проверява.
Формат: факти; 3 хипотези за NPS −7 + проверка; къде сме силни; напрежение; неизвестни; какво да не правя утре.
```

**Изход**

Факти: NPS надолу; activation нагоре; 47 vs 12 ≈ 4 спринта само за текущия backlog; 2 enterprise без root cause.

Хипотези: H1 incumbents нямат export/API (проверка: NPS по cohort). H2 trust/reliability, а requests са заместител на „не мога да си взема данните“ (CS Sev). H3 survey mix / 1 голям акаунт дърпа score-а.

Напрежение: Board може да чуе само wizard-а. 12 pts не мърдат mobile + API + export + churn.

Warning: не обещавай трите request-а. Не прави churn план без да говориш с двата акаунта.

## 4.3 Q3 Roadmap (Chaining, вход = 4.2)

**Prompt**

```text
Роля: PM с твърд WIP лимит.
Задача: приоритизация до Board (~2 спринта = 24 pts) и остатъка на Q3. Ползвай анализа. Не пренаписвай диагнозата.

Вход: [ИЗХОД ОТ 4.2]

Ограничения:
- Mobile НЕ влиза в Q3 build. Кажи какво казваме вместо да игнорираме искането.
- Не харчи 24/24 — остави резерв за enterprise fire-drill.
- Bulk export и API може да са един job-to-be-done — реши.

Формат: принципи; Now таблица (item, pts, защо, лост); Next; explicit no; какво казваме за mobile; рискове.
Без Board prose. Без churn playbook.
```

**Изход**

Принципи: данни/доверие преди нови повърхности; 30% резерв; тесни залози като wizard-а.

| Item | Pts | Лост |
| :--- | :---: | :--- |
| NPS разбивка по сегмент | 2 | Диагноза |

| Reliability buffer | 3 | H2 |
| Резерв fire-drill | 8 | 2 акаунта |

No: native mobile, „по малко от 47-те“. Към mobile: „чуваме го, Q3 е данни навън, Q4 go/no-go“.

*Защо:* резервът от 8 pts е мост към 4.4. Mobile се отказва с линия към клиента, не с мълчание.

## 4.4 Churn (Multi-Step, 3 хода, един чат)

Данните за клиентите ги няма в казуса — затова multi-step, не един prompt, който ще ги измисли.

**Ход 1**

```text
Роля: Principal CSM + PM. Не пишеш Board memo.
Контекст: NPS 34↓41, 2 unnamed enterprise, 12 pts, export/API вероятен лост, mobile не е Q3.
Задача: рамка за митигация. Данните за акаунтите ги НЯМА — не ги измисляй като факти.
Искам: 72ч discovery; 2 сценария (A platform gap / B relationship); какво НЕ правим; 5 въпроса, без които планът е театър.
```

**Изход:** Discovery = QBR, tickets, security questionnaires, champion, renewal, ARR. A = липсва API/export. B = тръгнал champion. Не правим: отстъпка като първи ход, private fork, mobile дата. Въпроси: renewal/ARR; писмен ли е churn; топ 3 нужди; конкурент; security блокери.

**Ход 2**

```text
Работни отговори:
1. Northwind HR — 180k ARR, renewal след 11 седмици. Helios People — 95k, след 5 месеца. Northwind е по-горещият.
2. Northwind: писмо от VP People „алтернативи ако няма API и export до края на квартала“. Helios: AE риск, usage пада след напускане на admin champion.
3. Northwind: API, bulk export, audit log. Helios: enablement, office hours, handover — не фийчъри.
4. Northwind — да, POC с конкурент. Helios — не.
5. Northwind: security questionnaire от 3 седмици без отговор. Helios — чисто.

Направи v1 план поотделно. Капацитет: 8 pts резерв до Board. Не кради целия Q3. Кой с кого говори тази седмица.
```

**Изход:** Northwind = platform + competitor + security lag → върни questionnaire, executive call, MAP, export (вече в roadmap), API като preview не GA. Helios = relationship → handover + office hours, **0 story points**. Два playbook-а, иначе Helios получава грешна медицина.

**Ход 3**

| :--- | :--- | :--- | :--- |

## 4.5 Board Summary

**Prompt**

```text
Роля: VP Product. Board. 10 мин четене.
Задача: един Q3 memo от трите входа. Не добавяй инициативи. Не крий NPS. Не продавай mobile.

Вход 4.2: [АНАЛИЗ]
Вход 4.3: [ROADMAP]
Вход 4.4: [CHURN ПЛАН]

Структура: контекст → какво работи → какво не → какво правим → какво искаме.

```

**Изход**

Activation е здрав (+18% wizard). Лоялността не е (NPS 34 срещу 41). 47 item-а при 12 pts. Два enterprise: Northwind (180k, API/export, конкурент, security lag) и Helios (95k, сменен champion — enablement, не API).

Asks: (1) WIP политика без native mobile, с 30% буфер; (2) CEO ескалация седмица 3 без изненадващ discount; (3) Q4 въпрос дали API е мултигодишна линия — тогава staffing, не още 47 tickets.

Риск, който не приемаме: да покрием NPS дупката с activation слайд.

## Финална рефлексия

**Кои три техники?** Decomposition в 4.1 (и Раздел 2). Chaining в 4.2→4.3 (и Раздел 1). Multi-step в 4.4 (и Раздел 3). 4.5 е синтез от трите, не само линейна верига.

**Най-предизвикателна?** 4.3 — 12 pts правят „не“ на mobile болезнено. 4.4 се чупи ако в ход 1 измислите факти за клиентите.

**Адаптация за работа:** декомпозирай артефактите преди чата; chain за анализ→решение→комуникация; multi-step за живи stakeholder неща; дръж поле „неизвестни“.

---

| Ако задачата е… | Ползвайте |
| :--- | :--- |
| Един артефакт + живи уточнения (JD, churn) | Multi-step |
| Анализ → приоритет → план → summary | Chaining |
| Голям лонч с успоредни отбори | Decomposition + синтез |
| Липсват факти | Кажи неизвестните; не chain-вай върху измислени числа |
